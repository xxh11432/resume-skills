# 项目亮点提炼与跨岗位映射

## 一、先纠正一个常见错误

「项目亮点」不是项目用了什么技术，也不是功能列表。  
亮点是：**在某个约束下，用户做了一个有难度的选择，并产生了可验证的结果。**

所以每个亮点至少要有三件事：

1. **约束 / 难点**：为什么不能随便做？
2. **动作 / 机制**：用户具体做了什么？
3. **结果 / 影响**：变快了、变稳了、变便宜了、能交付了，还是有可复用的产出？

只有「用了 Redis」「搭了微服务」「接了 LLM」，不叫亮点。

## 二、每个项目先填五格事实

在写任何简历句子之前，先为每个项目填完：

| 格子 | 要回答的问题 | 常见材料来源 |
|---|---|---|
| 背景 | 解决什么问题？给谁用？不做会怎样？ | README、PRD、产品说明 |
| 难点 | 最容易坏在哪？约束是什么（时间/成本/流量/数据/合规）？ | 代码复杂度、故障记录、用户口述 |
| 动作 | 用户具体负责什么？用了什么机制？为什么选它？ | 代码、提交、文档、用户确认 |
| 结果 | 有没有数字或可验证变化？ | 监控、压测、发布记录、用户数 |
| 取舍 | 放弃了什么？代价是什么？ | 设计文档、用户复盘 |

五格里缺两格以上，这个项目暂时只能写一句话，不能当主项目。

## 三、六类可写的亮点

按「证据强度」从高到低：

| 类型 | 长什么样 | 需要什么证据 | 适合岗位 |
|---|---|---|---|
| 性能 / 成本 | 延迟下降、吞吐提升、资源成本下降 | 压测或监控前后对比 | 后端、Agent |
| 稳定性 / 可靠性 | 故障率下降、幂等、降级、恢复时间缩短 | 告警、事故复盘、重试/补偿代码 | 后端、全栈 |
| 复杂架构 | 多服务拆分、数据一致性、异步链路 | 架构图、模块边界、关键代码 | 后端、全栈 |
| 端到端交付 | 从需求到上线独立完成 | 页面、接口、部署记录 | 全栈 |
| 效果 / 评估 | 准确率、召回率、成功率、成本下降 | 评估集、A/B、人工评测 | Agent、算法 |
| 从 0 到 1 / 创新 | 新系统、新流程、新工具落地 | 上线记录、采用人数、复用情况 | 全部 |

加分项：能讲清失败案例、监控与回滚、理论最优与团队可行之间的取舍。

## 四、亮点怎么选

一个项目通常能挖出 6-10 个点，简历只留 2-4 个。按四个标准打分：

1. **相关性**：和目标岗位的核心信号是否直接相关？
2. **稀缺性**：同届/同年限候选人里，这个点是否少见？
3. **可验证**：有没有代码、数据、上线记录支撑？
4. **差异化**：能否让用户从「做过类似项目」变成「解决过这个问题」？

排序时优先「稀缺 + 可验证」。相关性不够但很硬的点，可以放到技能栏或一句话带过。

## 五、简历句式：动作 + 机制 + 结果

推荐句式：

> **动词 + 对象 + 关键机制 + 结果**

示例：

- 弱：`负责订单系统的开发与维护。`
- 强：`重构 <strong>订单创建链路</strong>，用 <strong>本地消息表 + 定时补偿</strong> 解决支付回调丢失，线上订单不一致率从 <strong>0.3% 降至 0.01%</strong>。`

- 弱：`使用 Redis 提升系统性能。`
- 强：`为 <strong>热点商品详情</strong> 设计 <strong>多级缓存 + 单飞重建</strong>，挡住 <strong>Redis 击穿</strong>，大促期间接口 <strong>P99 稳定在 80ms 内</strong>。`

- 弱：`参与 AI 知识库项目。`
- 强：`搭建 <strong>混合检索 + 重排</strong> 链路，把知识库回答准确率从 <strong>62% 提升到 81%</strong>，单次问答成本降低 <strong>35%</strong>。`

### 写不出来时，按这个顺序补

1. 先补「用户做了什么」：没有动作，一切免谈。
2. 再补「为什么这么做」：有取舍才有工程判断。
3. 再补「怎么证明」：没有数字就找范围、对比、上线记录。
4. 最后才补「技术名词」：技术栈是证据，不是亮点本身。

## 六、同一项目，三个岗位怎么讲

这是多版本简历的核心。事实不变，**第一句和证据顺序变**。

| 维度 | 后端开发 | 全栈开发 | Agent 开发 |
|---|---|---|---|
| 第一句讲什么 | 系统在什么规模和约束下保持正确/稳定 | 用户从什么需求走到什么可用产品 | LLM 在什么任务上从不稳定变成可上线 |
| 最想证明 | 并发、数据一致性、性能、故障处理 | 端到端闭环、接口契约、交互与交付 | 检索/工具调用、评估、成本与兜底 |
| 项目条目顺序 | 架构 → 难点 → 机制 → 指标 → 取舍 | 需求 → 页面/交互 → API/数据 → 上线 → 结果 | 任务 → 方案 → 评估 → 指标 → 失败处理 |
| 技能栏顺序 | 语言框架 → 数据库/中间件 → 部署/监控 | 前端 → 后端 → 数据库/部署 | Python/框架 → 检索/向量库 → 评估/观测 |
| 应压掉的内容 | 页面细节、纯 UI 交互 | 过深的 JVM/GC 细节 | 与 AI 无关的 CRUD 细节 |
| 可以强化的内容 | 幂等、限流、缓存、分库分表、可观测性 | SSR/BFF、状态管理、响应式、Lighthouse | chunking、rerank、tool schema、eval、token 成本 |

### 示例：企业知识库问答系统

**后端版本**

- 设计文档解析与切片流水线，用 <strong>异步任务 + 失败重试</strong> 支撑 10 万级文档入库，单篇解析失败不影响整批任务。
- 为多租户检索增加 <strong>租户隔离 + 权限过滤</strong>，把越权召回从「靠提示词约束」改为存储层强约束。
- 对向量检索与关键词检索做 <strong>混合召回</strong>，将 Top-5 命中率从 68% 提升到 86%，P95 延迟控制在 400ms 内。

**全栈版本**

- 独立完成从文档上传、切片预览、问答对话到引用回溯的完整链路，前端用 <strong>React + SSE</strong> 实现流式输出与来源高亮。
- 设计 <strong>统一 API 契约与错误码</strong>，把上传、解析、检索、问答四类状态收敛到一套前端状态机，减少重复请求与状态错乱。
- 用 <strong>Docker Compose + Nginx</strong> 完成一键部署，补齐健康检查与日志面板，把交付时间从半天缩短到 10 分钟。

**Agent 版本**

- 搭建 <strong>混合检索 + 重排 + 引用约束</strong> 的 RAG 链路，回答准确率从 62% 提升到 81%，无依据回答占比降到 7%。
- 设计 <strong>工具调用 schema 与失败兜底</strong>，把检索超时、空结果、工具报错统一成可恢复状态，任务成功率从 74% 提升到 92%。
- 建立 <strong>50 条离线评估集 + 回归脚本</strong>，每次改 prompt/检索参数先跑评估，单次问答 token 成本降低 35%。

同一套事实，三种叙事。不要在后端版本里大谈 UI，也不要在 Agent 版本里只写「接了 LangChain」。

## 七、弱句改造清单

| 弱句 | 问题 | 改法 |
|---|---|---|
| 负责项目开发 | 没动作、没范围 | 写清模块 + 机制 + 结果 |
| 使用 Spring Boot 开发后端 | 技术栈不是成果 | 写解决了什么业务问题 |
| 优化了系统性能 | 没前后对比 | 补指标、口径、测试方法 |
| 保证了系统高可用 | 空泛 | 写单点、切换、降级、恢复 |
| 参与了 AI 项目 | 贡献模糊 | 写具体模块与个人产出 |
| 熟悉 Redis / Kafka / K8s | 无法验证 | 放到技能栏，并在项目里给证据 |

## 八、缺信息时怎么问（带选项）

- 「这个项目里你独立负责的是哪块？」  
  A. 全链路 B. 后端/接口 C. 前端/交互 D. 数据/检索 E. 部署/运维
- 「性能优化前后有数据吗？」  
  A. 有监控截图 B. 有压测报告 C. 只有体感 D. 完全没有
- 「这个项目最难的地方是？」  
  A. 高并发 B. 数据一致性 C. 检索效果 D. 交付周期 E. 线上故障
- 「项目是哪种起点？」  
  A. 从 0 到 1 B. 接手改造 C. Fork/模板二次开发 D. 课程/教程项目

## 九、最终自检

- [ ] 每个亮点都能在 30 秒内讲清「难点 → 动作 → 结果」
- [ ] 每个项目至少有一条只属于用户的动作，而不是通用职责
- [ ] 三个岗位版本的第一句不同，且各自指向岗位信号
- [ ] 数字都有出处；没有数字的条目用定性结果替代
- [ ] 没有为了岗位关键词而编造经历
- [ ] 团队项目写清了个人边界，fork/模板项目写清了增量
