# Agent 开发岗：版本写法

## 一、HR 和前 10 秒在找什么

Agent / LLM 应用岗不缺「会调 API 的人」，缺的是**能把不确定的模型变成可用产品的人**。简历先证明：

1. **任务定义**：你到底让模型解决什么问题，边界在哪。
2. **系统能力**：RAG、工具调用、工作流、记忆、多 Agent、结构化输出，至少有一项做深。
3. **评估与迭代**：不是「感觉效果不错」，而是有评估集、指标和回归。
4. **工程化**：延迟、成本、失败兜底、可观测性、上线。

只写「使用 LangChain 搭建 Agent」通常不够；要写「怎么知道它变好了、怎么防止它变坏」。

## 二、模块顺序

默认顺序：

1. 个人信息
2. 求职意向
3. AI / Agent 项目经历（前移）
4. 技术栈
5. 工作 / 实习经历
6. 教育经历
7. 其他（开源、论文、评测、博客）

如果 AI 项目是个人项目，放在工作经历前；如果有大厂 AI 实习，工作经历前移。

## 三、项目条目怎么写

每条 Agent 项目按「任务 → 方案 → 评估 → 工程」组织：

| 层 | 写什么 | 例子 |
|---|---|---|
| 任务 | 什么场景、输入输出、成功标准 | 企业知识库问答，答案必须带引用 |
| 方案 | 检索/编排/工具/记忆怎么设计 | 混合检索 + rerank + 工具调用 |
| 评估 | 用什么集合、什么指标 | 80 条评估集，准确率/引用命中率 |
| 工程 | 延迟、成本、失败兜底、观测 | 流式输出、超时降级、token 成本 |

推荐 3-4 条 bullet，第一条写系统与任务，第二条写核心机制，第三条写评估或指标，第四条写工程化/兜底。

### 可直接套用的句式

- `搭建 <strong>XX RAG 链路</strong>，用 <strong>混合检索 + 重排 + 引用约束</strong> 解决 <strong>XX 问题</strong>，准确率从 <strong>A 提升到 B</strong>。`
- `设计 <strong>工具调用 schema</strong> 与 <strong>失败兜底</strong>，覆盖 <strong>超时/空结果/参数错误</strong>，任务成功率从 <strong>A 提升到 B</strong>。`
- `建立 <strong>XX 条离线评估集 + 回归脚本</strong>，每次改 prompt/检索参数先跑评估，避免 <strong>XX 退化</strong>。`
- `优化 <strong>上下文与缓存</strong>，把单次问答成本降低 <strong>XX%</strong>，P95 延迟从 <strong>A 降到 B</strong>。`
- `为 <strong>XX 工作流</strong> 增加 <strong>人工确认/权限校验</strong>，把高风险动作收敛到可审计流程。`

## 四、技术栈怎么排

按「模型与框架 → 检索 → 评估与观测 → 后端工程」四组。

| 组 | 常见项 |
|---|---|
| 模型/框架 | Python、OpenAI / Claude / 通义 / DeepSeek API、LangChain、LangGraph、LlamaIndex、MCP |
| 检索 | Embedding、Qdrant / Milvus / pgvector、BM25、rerank、chunking |
| 评估/观测 | RAGAS、Langfuse、LangSmith、自定义评估集、日志与追踪 |
| 工程 | FastAPI、异步任务、Redis、Docker、流式 SSE、成本监控 |

不要把所有框架都列上。选 1-2 个真正用过的，项目里给出落点。

## 五、没有 AI 项目怎么办

不是所有人都要重写一个 Agent。可以从现有经历里翻译：

| 原经历 | 翻译成 Agent 岗的语言 |
|---|---|
| 搜索/推荐 | 召回、排序、评估、离线指标 |
| 数据管道 | 文档解析、清洗、chunking、索引更新 |
| 后端接口 | 工具调用、schema 设计、超时与重试 |
| 工作流系统 | 状态机、人工确认、权限与审计、MCP 工具接入 |
| 前端交互 | 流式输出、引用展示、失败提示 |
| 运维/监控 | 延迟、成本、成功率、告警 |

如果确实没有 LLM 项目，可以做一个小的真实项目，但必须包含评估和失败处理，不能只是聊天 demo。

## 六、校招 vs 社招

- **校招**：一个完整 AI 项目 + 评估意识即可；论文/开源/竞赛可作为补充。
- **1-3 年**：突出一个上线产品或完整链路，能讲清效果、延迟、成本三者的平衡。
- **3-5 年**：突出系统设计、评估体系、多 Agent/工具编排、稳定性与成本治理。

## 七、常见误区

1. **框架名堆砌**：LangChain、LlamaIndex、AutoGen 全写上，却讲不清自己写了什么。
2. **只有 demo，没有评估**：没有评估集，就无法证明效果。
3. **只讲效果，不讲成本**：token 成本、延迟、并发是 Agent 岗的硬指标。
4. **忽略失败**：检索为空、工具报错、模型胡说、超时，这些才是工程重点。
5. **把 prompt 当全部**：prompt 是手段，系统设计才是岗位。
6. **把「接入大模型」写成「自研大模型」**：边界要准确。

## 八、交付前自检

- [ ] 至少一个项目有明确任务定义和成功标准
- [ ] 至少一项核心机制能讲到实现层（检索、工具、编排、记忆）
- [ ] 有评估集或可验证指标，而不是「体验不错」
- [ ] 写了延迟 / 成本 / 成功率中的至少一项
- [ ] 写了失败兜底或权限/安全约束
- [ ] 技术栈里的框架能在项目中找到落点
