# 材料读取与证据台账

## 这份文件解决什么

用户扔过来的东西通常很杂：旧简历、项目压缩包、GitHub 链接、几段聊天记录、一张架构图。  
你的任务不是「都读一遍」，而是把它们变成一份**可追溯的事实清单**，再决定简历里能写什么。

**没有进入证据台账的内容，不得写进简历。**

## 一、按材料类型读取

| 材料 | 先做什么 | 重点提取 | 禁忌 |
|---|---|---|---|
| 旧简历 PDF | 按页拆图，逐页看 | 内容、模块顺序、字号与留白、被裁掉的内容 | 直接提文本，忽略排版与截断 |
| 旧简历 HTML / DOCX / MD | 读源文件 | 可复用的事实、原有结构与措辞 | 未确认的旧表述直接沿用 |
| 本地项目目录 | 先跑快照脚本，再读关键文件 | 技术栈、架构、核心机制、规模、部署、测试 | 扫 `node_modules`、`target`、`.venv`、构建产物 |
| GitHub 链接 | 确认仓库归属与可访问性，再读 README / 语言 / 目录 / 提交 | 项目定位、技术实现、活跃度、用户增量 | 把 fork、模板、教程项目写成原创 |
| 项目文档 / PRD / 设计稿 | 读目录与结论页 | 背景、目标、约束、方案取舍、指标 | 把规划写成已上线成果 |
| 截图 / 作品图 | 看图，不只看文件名 | 产品形态、页面结构、真实数据 | 图中看不清的数字不要猜 |
| JD | 提取 3-5 个硬性关键词 | 岗位信号、技术栈、经验年限、业务方向 | 按关键词编造经历 |

## 二、本地项目：读取顺序

### 1. 先跑快照

在 skill 根目录执行：

```bash
python scripts/project_snapshot.py --path <项目目录> --out <工作目录>/project-snapshot.md
```

快照会给出：git 信息、语言与代码规模、关键文件、顶层目录、最大源码文件。  
它只做盘点，不判断亮点；亮点仍要你读代码和文档后提炼。

### 2. 再按优先级读文件

1. **项目定位**：`README*`、`docs/` 首页、架构图、产品说明。
2. **技术栈证据**：`pom.xml`、`build.gradle`、`package.json`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`。
3. **运行方式**：`docker-compose.yml`、`Dockerfile`、`Makefile`、`.github/workflows/`、部署脚本。
4. **核心实现**：入口类、路由/控制器、领域服务、数据访问、中间件、消息消费者、定时任务。
5. **关键机制**：鉴权、缓存、锁、幂等、限流、重试、事务、检索、工具调用、评估脚本。
6. **数据与规模**：SQL/迁移文件、索引、分表分库、配置中的连接池/线程池/队列/超时。
7. **质量证据**：测试目录、压测脚本、监控配置、告警规则、CI 检查。

### 3. 读 git 历史（只在需要确认贡献时）

```bash
git log --oneline -20
git shortlog -sne --all
git log --author="<用户 git 名>" --oneline -20
```

用途：

- 判断项目是否持续维护、有没有真实迭代。
- 确认用户是否为主要提交者。
- 找关键版本节点（重构、性能优化、上线）。

注意：提交数不等于贡献质量；不要用提交数直接写「主导」。

### 4. 本地项目必须回答的 8 个问题

1. 这个项目解决什么问题？给谁用？
2. 用户负责哪几个模块？团队几人？
3. 技术栈是什么？哪几项是用户真正写过的？
4. 最难的工程问题是什么？为什么难？
5. 用了什么机制解决？有没有取舍？
6. 有没有规模数据：QPS、数据量、并发、延迟、成本、用户数？
7. 怎么部署、怎么监控、出故障怎么恢复？
8. 哪部分是从 0 到 1，哪部分是接手改造？

答不上来的，进入「待确认」，不要自行补全。

## 三、GitHub 链接：读取与归属确认

### 1. 先确认三件事

- 这个仓库是用户本人的、团队的，还是只是参考项目？
- 用户负责哪些模块？是不是 fork 或模板改造？
- 仓库是 public 还是 private？你能不能访问？

推荐直接给选项：

> 这个仓库和你是什么关系？  
> A. 我独立开发 B. 团队项目，我负责某模块 C. Fork/二次开发 D. 只是参考，不是我做的

### 2. 读取路径

优先顺序：

1. 有 GitHub 工具或连接器：直接读仓库元数据、README、目录、提交。
2. 能联网：`git clone --depth 1 <repo>` 到临时目录，再按「本地项目」流程读取。
3. 不能 clone：用 GitHub API 或网页读取：
   - `GET /repos/{owner}/{repo}`：描述、语言、fork 状态、默认分支
   - `GET /repos/{owner}/{repo}/languages`：语言占比
   - `GET /repos/{owner}/{repo}/readme`：README
   - `GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1`：目录结构
   - `GET /repos/{owner}/{repo}/commits?per_page=20`：近期提交
4. 私有仓库或网络不可达：请用户导出 zip、贴 README、或截取关键目录；不要假装读过。

### 3. 仓库里的高价值信号

| 信号 | 说明 | 能写进简历吗 |
|---|---|---|
| README 的架构图 / 模块说明 | 证明项目复杂度与设计 | 可写项目定位，不可直接写个人贡献 |
| 语言占比 | 技术栈证据 | 可写，需与用户实际参与一致 |
| 目录结构 | 分层、模块化、工程化 | 可写实现范围 |
| 提交历史 | 迭代、重构、修复 | 可写「持续迭代」，不可夸大 |
| CI / 测试 / 部署配置 | 工程成熟度 | 可写工程质量 |
| fork 标记 / 模板来源 | 项目起点 | 必须如实说明增量 |
| Stars / Fork 数 | 社区影响 | 一般不写；除非是项目核心成果且有上下文 |

### 4. 禁止

- 不读 `.env`、密钥、token、私有配置。
- 不把仓库里的 issue/PR 讨论当成用户本人观点。
- 不把「仓库有某功能」写成「用户实现了某功能」。
- 不在简历里放私有仓库地址或内部系统链接。

## 四、文档与截图

- PRD / 设计文档：先读「背景、目标、约束、方案、指标」五段，跳过格式与流程套话。
- 会议纪要：只取决策、分歧、取舍和用户动作。
- 截图：优先看有数据的页面（监控、压测、后台、产品页），记录图中能确认的数字与时间。
- 聊天记录：用户自己说的话才算证据；转述与他人评价只能作为线索。

## 五、证据台账模板

每读一份材料，就追加到工作目录的 `evidence.md`：

```markdown
# 证据台账

| ID | 事实 | 来源 | 置信度 | 是否需确认 | 适合岗位 |
|---|---|---|---|---|---|
| E1 | 项目使用 Spring Boot + MySQL + Redis | pom.xml / docker-compose | 已证实 | 否 | 后端 / 全栈 |
| E2 | 接口 P99 从 800ms 降到 220ms | 用户口述 | 待确认 | 是（要压测口径） | 后端 |
| E3 | 用户负责检索与工具调用模块 | 用户确认 | 已证实 | 否 | Agent |
| E4 | 项目为 fork，二次开发 | GitHub fork 标记 | 已证实 | 否 | 全部（需如实说明） |
```

### 置信度只有三档

- **已证实**：代码、配置、文档、用户明确确认。
- **待确认**：材料提到但口径不清，或只有间接线索。
- **冲突**：不同材料说法不一致。

### 使用规则

- 只有「已证实」能直接写进简历。
- 「待确认」先问用户；问不到就用定性表述，且不写具体数字。
- 「冲突」不写，直到用户给出取舍。
- 同一事实只保留一个主来源，避免简历里出现两个版本。

## 六、最少提问清单

材料读完后，最多问 3 个：

1. **归属**：每个项目你具体负责哪部分？团队几人？
2. **结果**：有没有监控/压测/发布记录能给出数字？
3. **方向**：三版同时投还是主投一个？目标届别/年限是什么？

如果用户只能回答一个，优先问归属。没有归属，项目写得再漂亮也不敢用。

## 七、什么时候停止读

- 已经能回答上面「本地项目 8 个问题」的 6 个以上。
- 已经有 4-6 个可写的候选亮点。
- 再读下去只是在重复同类文件。

一般一个项目读 10-20 个关键文件足够；超过 3 个项目时，只保留最强的 2-3 个，其余压成一句话。
